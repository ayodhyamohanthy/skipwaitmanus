## REL-watchdog: an external probe every 5 minutes that emails the owner (lane `watchdog`, Tier 2)
**Why.** D-100 approved "an external uptime check that alerts the owner ... after 2 consecutive failures"; it was never built. The stand-in, `.github/workflows/api-health-watch.yml` (cron `*/5`), ran 10 times in its first 32 hours, where about 390 runs were due, because GitHub delays scheduled workflows; and it probes `/api/health`, which answers 200 even when the schema failed and never touches the database (`server/healthRoutes.ts`). The Oct 22 outage lasted about 10 minutes and was found by hand (`docs/INCIDENT-2026-10-22-api-1101.md`). Cloudflare cron triggers fire on time.

**What.**
1. A separate Worker `skipwait-watchdog` in a new folder `watchdog/`: `watchdog/wrangler.jsonc` (its own `name`, `"triggers": { "crons": ["*/5 * * * *"] }`, `"workers_dev": false`, no routes, one KV namespace binding `WATCHDOG_STATE`), `watchdog/src/index.ts` (the `scheduled()` handler and I/O only) and `watchdog/src/core.ts` (pure: the probe list, result evaluation, the state machine, the email text). It imports nothing from `server/` or `client/`.
2. **Probes** (each with a 10 s timeout; read-only; none signs in, sends a code, writes a row or costs money):
   - `GET https://skipwait.me/` → 200 and the HTML holds `<meta name="git-commit"`.
   - `GET /api/health/ready` → 200 with `"state":"ready"`.
   - `GET /api/health/latency` → 200 and `dbRoundTripMs` is a number (that route answers 200 with `null` when the database fails).
   - `GET /api/plans/catalog` → 200 and the body parses as JSON (an HTML body is a failure).
   - `POST /api/auth/otp/send` and `POST /api/auth/workos/email-code/send` with the body `{"email":"watchdog-probe"}` → 400 JSON. Both handlers refuse a malformed email before any provider call or rate counter (`registerReferrerOtpLoginRoutes` in `server/_core/otpLogin.ts`; `server/_core/seekerEmailCode.ts`); re-read them first, and if that is no longer true, drop the probe and say so in the PR. A 5xx or an HTML answer here means sign-in is broken.
3. **When it alerts.** A round fails when any probe fails. A run probes; after a failed round it waits 30 s and probes again. Two failed rounds in a row open an outage (D-100's "2 consecutive failures"). State lives in KV (`{ state: "up" | "down", since, lastAlertAt, failing: [probe names] }`), written only when it changes, so writes stay far below the free limit. Up to down: one email "SkipWait DOWN: <probe names> (<status>)". While down: a reminder at most every 60 minutes. Down to up: one email "SkipWait recovered after <minutes> min". Every Monday at 03:30 UTC (09:00 IST): one "SkipWait watchdog: all probes green this week (<n> runs, <m> outages)" email, so a dead watchdog is noticed by its silence.
4. **How it emails.** The ZeptoMail HTTP API with the request shape `server/emailDelivery.ts` uses (copy the few lines; do not import it), to the two addresses in `server/errorAlerting.ts` (`ADMIN_ERROR_RECIPIENT`, `ADMIN_ALERT_COPY_RECIPIENT`), from `noreply@skipwait.me`. The watchdog Worker's one secret is `ZEPTOMAIL_API_KEY`. If a send fails, log it and leave the state unchanged so the next run tries again.
5. **Deploy.** `.github/workflows/deploy-watchdog.yml`: on push to `main` with `paths: [watchdog/**, .github/workflows/deploy-watchdog.yml]`, and on `workflow_dispatch`, run `npx wrangler deploy` in `watchdog/` with the existing `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`; then `npx wrangler secret list --name skipwait-watchdog`, and **fail the job** when `ZEPTOMAIL_API_KEY` is missing, printing the one-line owner command. Add it to `scripts/check-deploy-triggers.mjs` (`watchdog: { file: ".github/workflows/deploy-watchdog.yml", must: ["watchdog/**", ".github/workflows/deploy-watchdog.yml"] }`) so a later filter edit cannot silently stop its deploys.
6. **Keep the GitHub watch** (`api-health-watch.yml`) as a slow second layer. Do not delete it.

**Tests** (`scripts/watchdogCore.test.ts`, which Vitest already collects, importing `watchdog/src/core.ts`; add `"watchdog/**/*"` to the `include` list of `tsconfig.json` so `pnpm check` typechecks the Worker): each probe's pass and fail, including an HTML body on a JSON probe and a 5xx on a sign-in probe; one failed round opens nothing; two in a row open one outage and send one email; a further failed run sends nothing until 60 minutes pass; recovery sends one email with the minutes; the Monday note fires once a week; a failed send leaves the state unchanged; no email body holds anything but probe names, status codes and times.

**Owned paths.** `watchdog/`, `scripts/watchdogCore.test.ts`, `.github/workflows/deploy-watchdog.yml`, `scripts/check-deploy-triggers.mjs` (the new entry only), `tsconfig.json` (the include list only). Map line: "External watchdog". **Owner action** (the PR prints it; nothing alerts until it is done): `npx wrangler secret put ZEPTOMAIL_API_KEY --name skipwait-watchdog`, pasting the key the API Worker already uses. **Done:** tests, CI green, landed, deploy-watchdog green with the secret check, and proof that it alerts: run it locally with `wrangler dev --test-scheduled` against a URL that 404s (never a production change) and paste the subject of the email it sent.

## REL-5xx-capture: every server error reaches Sentry and the owner, sign-in and webhooks included (lane `observability`, Tier 2, after D-174-sample-job-removal, which also edits `server/_core/index.ts`; D-174-job-catalog waits for this one)
**Why.** 237 handled `status(500|502|503)` responses in 35 server files; 32 of those files never call Sentry (`git grep -lE 'status\((500|502|503)\)' -- 'server/*.ts' ':!*.test.ts'` on `02a8a028`). Nothing global reports a 5xx: the `/api` finish hook in `server/_core/index.ts` only logs slow requests. The owner's 5xx email (`materialErrorAlertMiddleware`, `server/errorAlerting.ts`) is registered after the payment and WorkOS webhooks and after the sign-in routes (`registerReferrerOtpLoginRoutes`, `registerReviewerLoginRoutes`, `registerPasswordResetRoutes`, the WorkOS and seeker email-code routes), so a broken sign-in code send or webhook emails nobody. The alert email and the user's sign-in codes share one sender, so a ZeptoMail outage silences its own alarm. tRPC `onError` sends every error to Sentry, 4xx included, which spends the free quota on noise.

**What.**
1. A new `server/httpErrorCapture.ts` exporting `httpErrorCaptureMiddleware`: for `/api` requests, on `res.once("finish")`, when `statusCode >= 500` and the request was not already reported (set `res.locals.errorReported = true` wherever a capture happens, `sentryErrorMiddleware`'s path included), capture one event with the fingerprint `[method, routeTemplate, String(statusCode)]` and tags only. `routeTemplate` is `req.baseUrl + req.route.path` when Express matched a route, otherwise `"unmatched"`; never `req.originalUrl`, `req.url` or a query.
2. In `server/_core/index.ts`, register `httpErrorCaptureMiddleware` and move `app.use(materialErrorAlertMiddleware)` to directly after `app.use(globalSecurityHeaders)`, before `registerPaymentWebhookRoutes`, so every `/api` route is covered. Nothing else in the file moves.
3. In `server/errorAlerting.ts`: the 5xx alert's dedupe key uses the route template (one systemic failure is one email; if FND-4 has landed, keep its scrubbed path in the email body), and `sendAdminAlertEmail` also raises a Sentry message carrying the subject only, so an email outage still leaves a trace.
4. In the tRPC `onError` in `server/_core/index.ts`, skip Sentry for `BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `TOO_MANY_REQUESTS`, `CONFLICT` and `PRECONDITION_FAILED`; keep every other code.

**Tests** (red first): a 503 from a route registered before the old position (a test app with a fake `/api/auth/otp/send` answering 503) produces one capture and one alert, keyed on the template; a 400 or 404 produces neither; an error that reaches `sentryErrorMiddleware` is captured once, not twice; `/api/referrer-review-links/abc123` answering 500 gives a fingerprint and an alert key without `abc123`; an admin alert whose email send fails still produces the Sentry message; the tRPC filter skips `UNAUTHORIZED` and keeps `INTERNAL_SERVER_ERROR`; a source-pin test asserts both middlewares are registered before `registerPaymentWebhookRoutes` in `server/_core/index.ts`.

**Owned paths.** `server/httpErrorCapture.ts` and its test (new), `server/_core/index.ts` (the registrations and the tRPC `onError` only), `server/errorAlerting.ts` (the alert key and `sendAdminAlertEmail` only) and their tests. Do not edit `server/sentry.ts` (FND-4) or any sign-in or payment file. **Done:** tests, CI green, landed, and one real production event in Sentry, or, if none occurs within a day, the result of `POST /api/admin/alerts/test` and its Sentry link.

## REL-release-verify: after every deploy, a machine checks the live release and says so (lane `deploy-workflows`, Tier 2)
**Why.** A deploy is verified only by its SHA (`deploy-api.yml`'s readiness and admin gate; `deploy-pages.yml` reads the `git-commit` meta). Both deploy workflows post their result as a comment on whichever issue is newest. `rollback.yml` has never run: `target: web` has no job, and a blank commit redeploys the current `main`, not the previous release. `drift-watch.yml` raised false drift for weeks (issues #94 and #475, now closed; the side-branch bug is fixed by `d36238fc`), checks the API alone, still fires while a normal 15 to 40 minute rollout converges, and runs only every few hours on GitHub's schedule. After a release the web can call an API that is still rolling out (15 to 40 minutes, `scripts/deploy-cloudflare-two-phase.sh`), so new client code may hit routes the live API does not have yet. Nothing records that a release was checked end to end.

**What.**
1. `scripts/release-smoke.mjs` (read-only; no sign-in, no writes, no money), with its pure part in `scripts/releaseSmokeCore.mjs`: given a base URL, an expected API SHA and an expected web SHA, it checks `/` (200, `git-commit` meta equals the web SHA), `/api/health` (`commitSha` equals the API SHA), `/api/health/ready` (ready), `/api/health/latency` (`dbRoundTripMs` is a number), `/api/plans/catalog` (200 JSON with the keys `client/src` reads), `/sitemap.xml` (200), one signed-out API the client calls only when signed in, which must answer 401 (name it in the PR), and the admin sign-in redirect (302, as `deploy-api.yml`'s admin gate checks). Then a signed-out Playwright pass over the public pages `scripts/live-flow-audit.mjs` lists, failing on any console error or 5xx (that script only logs them). It prints one line per check and exits non-zero on any failure.
2. `.github/workflows/release-verify.yml`: `on: workflow_run` for "Deploy API" and "Deploy Web" (`types: [completed]`, branch `main`) plus `workflow_dispatch` with a SHA input. The expected web SHA is the newest `main` commit at or before the run's `head_sha` that touched a path in `deploy-pages.yml`'s filter, and the expected API SHA the same for `deploy-api.yml` (read both filters from the workflow files; do not copy them). If a newer `main` commit has its own deploy running, exit as superseded. Wait up to 45 minutes for the API to serve its SHA, then run the smoke. Result: a commit status `release/verified` on the run's `head_sha` (`permissions: statuses: write, issues: write`). On failure, open or update one issue `Release not verified: <sha8>` labelled `incident` with the failing lines; on the next verified release, comment on and close every open `Release not verified` issue.
3. Both deploy workflows: replace the "Notify" step's comment on the newest issue with: on failure, open or update one issue `Deploy failed: <workflow name>` labelled `incident`; on success, close it if open. In `deploy-api.yml`, run the readiness and admin-gate steps with `if: always() && steps.<deploy step id>.outcome != 'skipped'`, so a failure in the middle of a deploy still checks what went live.
4. `deploy-pages.yml`: when the same push changed API paths (reuse `scripts/classify-api-changes.sh`), wait before `pages deploy` until `/api/health/ready` reports that SHA (up to 45 minutes; then deploy anyway and open the `Deploy failed` issue saying the API did not converge), so the web never runs ahead of the API it needs (AGENTS.md invariant 6).
5. `rollback.yml`: add a `rollback-web` job (build the given ref and `wrangler pages deploy` it with the commands `deploy-pages.yml` uses), so `target: web` and `target: all` work; the API job defaults to the previous successful Deploy API run's SHA instead of `github.sha`, stamps `API_RELEASE` and waits for readiness the way the deploy does. It stays manual (the owner or the fix-main agent). Do one drill: roll the web back to the release before and forward again on a quiet hour, and paste both run links.
6. Delete `.github/workflows/drift-watch.yml`; release verify and REL-watchdog replace it.

**Tests** (red first, `scripts/releaseSmoke.test.ts`): each check's pass and fail on fixture responses (HTML on a JSON route fails; a console error fails; a 5xx on a public page fails; `dbRoundTripMs: null` fails); the expected-SHA rule picks the newest commit that touched each filter; a superseded run exits without a status.

**Owned paths.** `scripts/release-smoke.mjs`, `scripts/releaseSmokeCore.mjs`, `scripts/releaseSmoke.test.ts`, `.github/workflows/release-verify.yml` (new), `.github/workflows/deploy-api.yml` and `.github/workflows/deploy-pages.yml` (the Notify steps, the `if:` lines and the API wait only; leave the `paths:` filters as they are), `.github/workflows/rollback.yml`, `.github/workflows/drift-watch.yml` (delete). Map lines: "Container/runtime deploy" and "Pages deploy". **Done:** tests, CI green, landed, the drill links, and the link to the first `release-verify` run on `main` with `release/verified` green.

## REL-heartbeats: the watchdog sees a stopped scheduler and a broken dependency (lane `jobs`, Tier 2, after REL-watchdog and REL-5xx-capture)
**Why.** If the hourly cron, the tick or the job store stops, payment reconcile, coverage delivery, the D-038 timers and the money check all stop, and nobody hears: the overdue flag (`OVERDUE_WINDOWS` in `server/scheduledJobsRoutes.ts`) is computed only when someone opens `/api/admin/jobs`, and no client calls it; a job that exhausts its attempts is skipped silently. The daily money check emails only when it finds something, so a clean day and a day it never ran look the same. `/api/health/ready` reflects schema reconciliation only.

**What.**
1. `GET /api/health/jobs` (public, `no-store`, cached 60 s in process): `{ ok, jobs: [{ name, overdue }] }` for every registered job, with `overdue` computed by the same rule as the admin read (export that rule from `server/scheduledJobsRoutes.ts` and use it in both places). Names and booleans only: no times, counts, ids or errors. `ok` is false when any job is overdue or the job store cannot be read.
2. `GET /api/health/deps` (public, `no-store`, cached 60 s): booleans only: `db` (a trivial query succeeds within 3 s), `email` (a sender is configured), `workos` (configured), `chargebee` (configured). Never a key, host or error text. Not used by the deploy gate.
3. In `watchdog/src/core.ts`, add two probes: `/api/health/jobs` answers 200 with `ok: true`; `/api/health/deps` answers 200 with every boolean true. They join the two-round outage rule.

**Tests** (red first): a job whose last success is older than its overdue window reads `overdue: true` on both reads; an unreadable job store gives `ok: false` and still answers 200; the bodies hold no field beyond the contract (pin the key set); the new probes fail on `ok: false`.

**Owned paths.** `server/healthRoutes.ts`, `server/scheduledJobsRoutes.ts` (export the overdue rule only), `server/_core/index.ts` (the `registerHealthRoutes` deps only), `watchdog/src/core.ts` and `scripts/watchdogCore.test.ts`, their tests. Map line: "Health and release identity". **Done:** tests, CI green, landed, and `curl https://skipwait.me/api/health/jobs` output in the PR after the deploy.

## REL-review-email-retry: a referrer's review email that failed is sent again (lane `notifications`, Tier 1; D-174-job-catalog and D-174-pool-nudges wait for this one, since all three register a scheduled job)
**Why.** When a seeker sends a referral request, verified employees get a review email (`dispatchReferralReviewDeliveries` in `server/referralReviewDispatch.ts`, fire-and-forget, once). A failed send is stored with `status` `failed` or `unknown`, an `attemptCount` and a backed-off `nextAttemptAt` (`completeReferralReviewDelivery` in `server/db.ts`), and `claimReferralReviewDelivery` already accepts such a row again while `attemptCount < 5`, but nothing ever retries it. The referrer never hears of the request and the seeker waits for nothing.

**What.**
1. An hourly job `review-delivery-retry` (registered in `server/scheduledJobRegistry.ts` and `shared/scheduledJobs.ts` like the others): read up to 50 email delivery rows with status `failed` or `unknown`, `nextAttemptAt <= now` and `attemptCount < 5`, oldest first. Skip a row unless the request can still be reviewed by that referrer (still open, not withdrawn or closed, not blocked either way, `server/blockedPairs.ts`). Otherwise claim it with `claimReferralReviewDelivery`, send it, and record the result with `completeReferralReviewDelivery`, exactly as the first attempt does.
2. **The link.** The first attempt gets each raw `linkToken` from `prepareReferrerReviewEmailNotifications` at send time. Read how that function stores the token. If the raw token is stored only as a hash, the retry must re-issue the link for **that referrer only** (never for a referrer whose email was already sent, whose link must keep working) and must never store a raw token; if neither is possible, stop and report.
3. When a row reaches 5 attempts, alert the owner once (`sendAdminAlertEmail`) with the request id and channel only.
4. `server/emailDelivery.ts`: keep the provider's HTTP status in the thrown error, so `lastError` records it.

**Tests** (red first): a failed row past its `nextAttemptAt` is sent once and marked `sent`; a row not yet due, a sent row, a revoked row and a row at 5 attempts are untouched; a withdrawn, closed or blocked request is skipped; two runs in the same window send once (the lease); a retry never changes another referrer's working link; the fifth failure alerts once; no raw token is written anywhere.

**Owned paths.** `server/reviewDeliveryRetry.ts` and its test (new; the due-rows query lives here, not in `server/db.ts`, which many money rows hold), `server/scheduledJobRegistry.ts` and `shared/scheduledJobs.ts` (one entry each), `server/emailDelivery.ts` (the error text only) and its test. If step 2 needs a change in `server/db.ts`, stop and ask the CEO to widen the row's `owns`. Map line: "Scheduled jobs". **Done:** red-first tests, CI green, independent review passed (Tier 1: it emails real people), landed, and the job's first run shown as succeeded in `/api/admin/jobs` (or `/api/health/jobs`).

## REL-client-capture: a failed call in the browser is recorded (lane `observability-client`, Tier 1, after FIX-device-signin, which edits the same sign-in forms)

**What.**

2. `client/src/main.tsx`: send React Query and mutation errors that are not a 4xx to `captureClientError`, and report the "Unexpected token '<'" case as `api_html_response` instead of dropping it.

**Tests** (red first): `apiFetch` reports a 503, an HTML body and a network error once each and returns or throws exactly what `fetch` did; a 400 is not reported; the route tag carries no token; the four components' existing tests pass unchanged.

**Owned paths.** `client/src/lib/apiFetch.ts` and its test (new), `client/src/main.tsx` (the error handlers only), the four components (the `fetch` call only). **Done:** red-first tests, CI green, independent review passed (sign-in surfaces), landed, captures at 1280 and 390 of each sign-in screen showing no change.

## REL-webhook-auth-alarm: a payment webhook refused for its secret is noticed (lane `payments-ops`, Tier 1)
**Why.** `server/chargebeeRoutes.ts` answers a webhook with a bad or missing secret with 401 and records nothing. If the secret drifts, every refund, card-validation and renewal event is refused, the hourly reconcile covers only checkouts SkipWait started, and nobody is told.

**Tests** (red first): a 401 writes one row and one capture; a burst inside 10 minutes captures once; a valid webhook writes neither; the money check reports the finding from a seeded row and stays silent without one.

**Owned paths.** `server/chargebeeRoutes.ts` (the 401 branch only), `server/dailyMoneyCheck.ts` (one finding only), and tests named `server/chargebeeRoutes*.test.ts` and `server/dailyMoneyCheck*.test.ts`. **Done:** red-first tests, CI green, independent review passed (payments file), landed.

**Tests** (red first, rows seeded through the real writers, never hand-written shapes): each finding fires on its case and stays silent on its control; the job writes nothing; the email holds counts and ids only.
