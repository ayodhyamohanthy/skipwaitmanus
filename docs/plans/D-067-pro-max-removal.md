## Risks

- The owner's statement that no Pro/Max users exist is load-bearing, since there is no dry run (D-067). If a live Chargebee Pro/Max subscription exists, the deploy moves that person to Free immediately: Pro drops from 10 to 3 open asks, Max loses assistants, and leftover cycle credits expire on the next read or the hourly plan-credit-cycles run. Chargebee keeps renewing, and each renewal lands as an unmatched paid invoice (admin alert) that grants nothing. getUserSubscription (server/db.ts:3221) returns nothing once plan is 'free', so /billing cannot self-cancel the still-live provider subscription. The only recovery is a human cancel and refund in the Chargebee dashboard; record it in PAYMENTS_TEST_RUNBOOK §7. Agents never touch live Chargebee.
- Storage contracts are destructive if touched. Removing pro/max from WALLET_PLAN_IDS/INTENT_PLAN_IDS, moving 'monthly' out of first place in BILLING_PERIODS, or editing giftSubscriptionFulfillments ENUM('pro','max') reorders or shrinks a MySQL ENUM, which the 0090/0091 contract tests pin. Shrink only the billable and entitled lists.
- The gate has blind spots. `pnpm check` (tsconfig) excludes **/*.test.ts and all of scripts/, and the vitest include has no shared/**/*.test.ts, so shared/assistant.test.ts never runs. A dangling SUBSCRIPTION_PLANS import in scripts/prerender-public-pages.tsx only fails in scripts/prerender*.test.ts and in `pnpm build`, which runs `tsx scripts/prerender-public-pages.tsx`, meaning at deploy. Run the full quality gate including build, and put new tests in server/ or client/src/.
- Import cycle: shared/billingCatalog.ts imports shared/planEntitlements.ts. Making isPaidPlanActive and paidPlanLapsed catalog-aware must use CATALOG_PLAN_IDS from shared/planCatalog.ts, not isBillablePlanId/isCatalogPlanId from billingCatalog.
- Choice of 'reads as Free' mechanism. Removing fromLegacy alone makes entitlements and subscription state Free, but an active pro wallet keeps plan 'pro' in /api/credits/summary. The client's hasActivePaidPlan then shows a paid plan with a raw 'pro' label and a Cancel button, and the wallet keeps opening 'paid' cycles at Free's 3 credits until the term ends plus the 3-day grace. Recommended, 8/10: treat any non-free plan outside the catalog as lapsed now, in paidPlanLapsed, isPaidPlanActive and normalizedWalletState, so the existing ledger roll writes Free with expiry and grant rows. This keeps one source of truth and a full ledger trail, and the hourly job sweeps leftovers. Counter-argument: it writes to legacy wallet rows. The no-write alternative maps plan to 'free' in creditSummaryFromWallet.
- Gifts sell only Pro/Max. GIFT_CHECKOUT_ENABLED is not forwarded by src/worker.ts, so production always answered 503 and SkipWait never sold a gift. But the webhook excludes gift invoices from the unmatched alert (`giftPaid`, chargebeeRoutes.ts:364), and fulfilment or claim would write a pro/max wallet (giftWalletPatch). If fulfilment is removed and the exclusion kept, a paid gift becomes a silent loss, which breaks the payments bar. Keep receipts, never fulfil, alert. Keep gift-checkout at 503 for the BUGFREE 4.9 battery. Remove both gift env flags from code and .env.example together, or configContract.test fails.
- DM refusal coupling. server/dmRoutes.ts:131 maps the in-transaction error by regex `/premium feature/i → 402`; changing the db.ts message without changing the mapping turns the refusal into a 500. Use a typed error. Update Messages.tsx:125 and messagesIdempotency.test.tsx:267 with it.
