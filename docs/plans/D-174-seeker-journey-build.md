## 1. Goal
The owner's journey (D-174): type a company, pick it, see its live jobs, filter, pick a job, request a referral, answer a few questions, add a resume, send. If someone at the company can refer, it goes to them; if not, it waits in the company's pool for whoever verifies later. #612 built the first slice (the company door: pick a posted role, ask in place). This packet covers what remains after #612 (D-189 (2)): search that suggests companies, the company's jobs with filters including seniority, a job-locked request, D-176's post-save line, and a ruling on how the per-company state before sending fits D-176. It also adds the row that drops `openToReferrals`/`openCount` from the public `GET /api/companies` payload (D-193 (5)).

**How this moves the goal.** A seeker reaches a sendable request in fewer steps (no job link to hunt for when the company's careers board is verified) and is never shown a company as closed, which on Oct 24 discouraged requests at 37 of 39 directory companies (production marked two open, D-193 §3.8) that the pool would route anyway. Seeker mental model (owner's words, D-176): "they just search company, see job ids and its descriptions, they ask referrals". They expect to ask at the company they want; they fear wasting money and being ignored. The pre-send line in §4.1 tells them the one thing that is true everywhere (nothing is used until a verified employee can see it); the post-save line tells them what actually happened. Referrers see nothing new from these rows.

## 4. Rulings (changeable assumptions until their register entry lands; each rated, strongest objection first)
1. **Before sending, every company looks the same (8/10).** The door, the drawer and `/ask` stop reading availability. The door shows no open or not-open status, one primary "Request a referral" for every company, and `ASK_COST_SENTENCE` under it. The drawer and `/ask` show "Only verified {Company} employees can see it" for every company (true either way: only that company's verified employees ever see a request, per the BRIEF; it is a privacy statement, not a status). The composer prices every company with the path it already uses for a company it cannot match (`askCostLine({ open: null, ... })`), which is true whichever way the server routes: nothing is used until a verified employee can see it. *Why above 7:* it is the only pre-send state that is true at every company and reveals nothing (D-176), it reuses a shipped and tested path instead of new money copy, and it needs no server or ledger change. *Against:* a seeker with no credit at one of the few companies that has an available referrer learns of the shortfall on Send (the server's existing refusal, draft kept) instead of before writing. Production marked two of 39 companies open on Oct 24 (D-193 §3.8), so this is the rare case.
2. **The D-132 flag-on guard loses its client input, and nothing else moves (7/10).** With availability unknown, the composer never sends `expectedCoverage`. The server guard (`server/db.ts:1918-1919`) and its server tests stay byte-identical; with `ASK_LEVEL_COST` off (today, and superseded by D-219) nothing a seeker sees or pays changes. The flag-on composer pins at `ask.costQuote.test.tsx:287-450` that assert a free-wait line or a sent `expectedCoverage` are re-pinned to the unknown-coverage line and no `expectedCoverage`; nothing else in that file changes. *Against:* it edits tests of a pricing-flag contract while pricing work is held. It changes no price, plan content or charge point. §8 Q1 asks the coordinator to confirm.
3. **"Get told when a referrer joins" leaves the ask path (6/10).** The control exists only where no one is available, so showing it is a status. The pool already delivers the request when someone joins (D-174). `/alerts` and the server alert path are untouched (their owners are `D-057-session-gate` and `DECISION-COPY-oct26`). *Against:* it removes a low-commitment option for a seeker not ready to send.
4. **Post-save, the routing clause speaks the owner's words (8/10).** Headline "Referral request sent to {Company}." (D-180). The detail's first clause becomes "It reached verified {domain} employees." (covered) or "It's waiting in {Company}'s pool for verified employees who join, so nothing was spent." (waiting). Every other clause, including every expiry clause, stays byte-identical for `D-174-expiry-clock-removal`. *Against:* small copy churn on a pinned string.
5. **The public payload drops availability by expand-then-contract (7/10).** `GET /api/companies` and `/api/companies/:slug` stop sending `openToReferrals` and `openCount`; `publicCompanySchema` keeps `openToReferrals` as optional and `companyDirectoryResponseSchema` keeps `openCount` optional for one release, so the 27 test files that carry the key in fixtures (17 client, 10 server, by `git grep -l openToReferrals` on `f5b9afb9`) still type-check and no test file outside the row is touched. `adminCompanySchema` declares `openToReferrals: z.boolean()` itself, so admin views keep it. `companyClaim.ts` reads availability from a new internal getter (`getCompanyDirectoryRecord(slug): Promise<AdminCompany | undefined>`), not the public shape. `CoverageBlock` shows only the seeker's own requests from their server state (`queueStatus`), never directory companies. Removing the optional keys and fixture values is a later cleanup row (§9). *Against:* a dead optional field lives one release; `CoverageBlock` loses its teaching state for a seeker with no request yet.
6. **Seniority filter = the catalog's level (8/10).** Filters are the facets the jobs route returns: location, level (labels from `JOB_LEVEL_LABELS`, D-110) and function. No band grouping until D-219's L1-L10 to band mapping is decided, and no price in the filter. *Against:* ten level chips are more than a seeker needs; the band mapping will regroup them later.
7. **Honest job states (9/10).** `completeness: "unavailable"` (or `source: null`) shows "We can't list {Company}'s jobs yet. Paste a job link to request a referral." with the link path; `"partial"` shows "From {Company}'s careers site, updated {date}. This may not be every opening."; `"complete"` shows the source line without the second sentence. Never "0 jobs", never "all jobs" unless complete. Employee posts (D-022) stay first; a sponsored item only as labelled Featured (D-040). No `JobPosting` markup.
8. **An unlisted company is a link, not a dead end (8/10).** With no suggestion, the primary action is "Paste a {typed name} job link to request a referral", which opens `/ask` with the link field focused (pasted links at unlisted companies already create a waiting request, D-193 §3.5). "Request a company" (`/invite`) stays as the quiet secondary link until the D-086 rows decide that surface.
9. **Linkless posts stay with D-177 (9/10).** A post without a public link is D-177's employee-shared type, unbuilt; its packet adds the drawer state. These rows add nothing for it, and `D-174-fix-post-binding`'s read-only link state covers posts that have a link.
10. **One release row (7/10).** `D-174-seeker-journey-build` turns on the client switches of `.search` and `.jobs-list` only after `.job-ask` lands, QA on the preview, an independent review and the CEO's sign-off. `JOB_CATALOG_ENABLED` stays QA's switch (D-193 §5.5). *Against:* typeahead sits dark until the long `.job-ask` chain clears (it waits for `D-174-ask-from-job`, which waits for `D-174-held-ask-reconfirm` and through it `D-090-BYOR`); §8 Q3.
