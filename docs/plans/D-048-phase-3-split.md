# D-048 phase 3 split: many agents, one goal UI rollout (D-126)

> Read [`docs/BRIEF.md`](../BRIEF.md) first. Decided by Claude Code as CEO under D-109 on Oct 21 2026, from a read-only study of the code (eight agents: surface map, rollout map, shared hotspots, picker mechanics; three designs judged). The register wins any conflict. Nobody picks a row from this file by hand: rows enter `docs/plans/assignments.json` as described below and `node scripts/next-task.mjs` hands them out.

## Why the rollout was serial
All D-048 rows shared the lane `design`, and the picker allows one open pull request per lane, so phase 3 could only move one page at a time. Lanes are free strings: splitting the lane is a data change. What makes parallel work unsafe is a short list of shared files, which one foundation chain now owns: the route table (`client/src/App.tsx`, all 87 routes on one line), the app shell, `client/src/components/goal/**`, the goal boundary test's allowlist, tokens and kit files.

## The method
1. **Foundation first** (lane `design-core`, one agent, in order): type scale (#379), the flag module (`client/src/lib/goalSurfaces.ts`: every surface id pre-declared, a `RELEASED` list in code, off by default), the W0 shell switch (#361 reworked), shared primitives, the test harness, the credits hook, the static frame for prerendered pages. Route-table reformatting (`D-048-F-routes`) runs beside it in its own lane.
2. **Cluster lanes**: pages are grouped by the code they share (import graph), not by audience, so up to 13 lanes build at once and no two lanes edit the same file.
3. **Every page lands dark**: the goal version lives in new files under `client/src/pages/goal/<id>/`; the existing page file gets only a three-line switch (`goalSurfaceOn('<id>') ? <GoalX/> : <KitX/>`); kit components and kit tests are never edited or deleted. Data and API modules are imported read-only, so money, credit, identity and privacy logic stays one code path.
4. **Releases are one-line pull requests** that add ids to `RELEASED`, one per wave (R1-R7). A release row waits for the owner's yes on the 1280 and 390 captures (or the delegation he chooses). Production always equals the code on the main SHA.
5. **Retirement** removes the kit version only after 7 days live with no new Sentry issue.

## Landing, every row
Every surface lands dark and green under D-082, one landing at a time. Going live is a separate, reviewed one-line PR. 

**1. Claim.** - Run `node scripts/next-task.mjs --claim "<model>"`. - The picker hands out a surface only when its lane is free and its dependsOn are done. - Lane packets set each row's packet and status to todo in the packet PR. Until then the rows stay architect. That is required, because validateAssignments refuses a todo row with no packet. - Every new branch slug must match no existing remote branch. workBranchOf matches tasks to branches by slug (nextTaskCore.mjs:164-170), so a stale branch such as agent/opencode/d048-phase-3-find would be taken as the task's work. 

**2. Build.** - The goal version goes in new files under client/src/pages/goal/<id>/. - The existing page file gets only a switch:   - rename its default export to KitX;   - export a default that returns `goalSurfaceOn('<id>') ? <GoalX/> : <KitX/>`;   - GoalX is React.lazy, or a static import on the 12 prerendered pages. - Kit components and kit tests are untouched. - Data and API modules (*Api.ts, inboxThreads.ts, referrerData.ts, billingApi.ts, threadApi.ts, shared/moneyCopy.ts) are imported read-only, so money, credit, identity and privacy logic is one code path for both versions. - A surface never edits:   - App.tsx, AppShell.tsx, or anything under client/src/components/goal/**;   - index.css, kit.css, kit/** or ui/**;   - hooks/** or shared lib/**;   - shared/** or server/**;   - assignments.json, DECISIONS.md, AGENTS.md, BRIEF.md or the §3b row. - If it needs one of those changed, it stops and reports to the design-core lane with evidence (D-032). 

**3. Local gate.** - `pnpm check`. - The page's kit tests, unedited. They run with the flag off: goalSurfaceOn ignores RELEASED in test mode. - New goal tests with the flag forced on via `vi.mock('@/lib/goalSurfaces')` and client/src/test/goalShellHarness.tsx. They port the kit behaviour assertions: the same API calls, plus the loading, empty, error and offline states. - On sign-in or referrer surfaces, with the flag on: the login-rule pins (loginRule, signIn, verify, referrer.otp). - `node scripts/design-token-audit.mjs` (it covers pages/goal/** after F-flags). - `VITE_GOAL_SURFACES=all pnpm build`, which also prerenders the 12 public pages. - `pnpm quality:gate`. - Captures at 1280 and 390: `node scripts/kit-screens/capture.mjs --goal <ids> --fixture scripts/kit-screens/fixtures/00_goal-*.json --viewport both`, committed to design/goal-ui/captures/<id>/ and compared with design/goal-ui/pick/*.png. 

**4. Pull request.** - Push the branch and open a PR: a draft for Tier 1, with an independent review by a session that did not build, fix or review it (D-109d). - Required checks: typecheck, unit + component + route tests, production build (which now includes the flags-on build). - Surface PRs touch only client/** and docs/design, so landing triggers only deploy-pages (median 1.6 min), never deploy-api (median 16.4 min). 

**5. Land.** - Take the landing slot. Until the picker has one, announce it with `--report` and land strictly one at a time. - Merge the latest origin/main and re-run `pnpm quality:gate`. - Check that `git diff --name-only origin/main...HEAD` stays inside the task's owned paths. - Run `git merge-tree $(git merge-base origin/main origin/<a>) origin/<a> origin/<b> \| grep -c '^+<<<<<<<'` against every other open D-048 branch. The count must be 0; anything else goes to the CEO. - Push, wait for every check green on that exact SHA, then `git push origin <sha>:main`.   - Never the merge button: strict up-to-date checks are off on ruleset 25433342, so a stale green PR could land an untested merge.   - Never squash. - Watch main CI and deploy-pages to the end, then release the slot. - Production does not change, because RELEASED does not list the id. Confirm with `scripts/verify-live-release.sh`. 

**6. Release, per wave.** - The release row stays status owner until the owner says yes to the wave's captures. - Then a kit-drift check: `git log <surface landing SHA>..origin/main -- <kit page + its exclusive files>` must be empty, or the change is ported into the goal version first. - Re-run the surface's behaviour tests with the ids on. - A one-line Tier 1 PR adds the ids to RELEASED in client/src/lib/goalSurfaces.ts and lands through the same D-082 steps. - After deploy: `node scripts/live-flow-audit.mjs --base=https://skipwait.me`, a signed-in check at 1280 and 390, and 24 h of Sentry watch on those routes. - Rollback is a revert of that line: about 6 min to production (PR CI about 4.4 min, then deploy-pages about 1.6 min). The kit is still in the code. 

**7. Retire.** - After 7 days live with no new Sentry issue, that wave's K row deletes the kit bodies, switches, kit-only components and kit tests. - D-048-K-kit deletes the kit layer last. 

**8. Docs (D-068).** - A surface PR writes its status in its own packet section. - The CEO rolls up assignments.json, the §3b row, AGENTS.md and BRIEF.md in one tracker commit per batch of landings. BRIEF.md has 197 bytes left under its 10,240-byte cap.

## Bug controls
- Kit path is untouched and its tests are the proof: a surface PR changes only a 3-line switch in the page file and never edits or deletes an existing test. #360 as built deletes client/src/pages/myRequests.kit.test.tsx (158 lines), which would break D-082 (6); the rework restores it.
- Test-mode rule: under vitest, goalSurfaceOn ignores RELEASED and reads only VITE_GOAL_SURFACES (empty by default). Releasing an id therefore never makes unedited kit tests render the goal page. goalSurfaces.test.ts pins the RELEASED list, rejects unknown ids and checks the needs-shell rule directly. None of the three designs had this; without it every release would turn CI red.
- Off by default with production truth in code (D-097): RELEASED is a versioned list in client/src/lib/goalSurfaces.ts, and deploy-pages.yml never passes VITE_GOAL_SURFACES (today it passes only WORKOS, SHA, Sentry and Clarity keys). A main SHA therefore always renders exactly what its code says. #375's shareFlags.ts reads VITE_SHARE_WIN_CARD instead, a pattern that cannot be turned on in production without a workflow edit.
- The frame follows the body: AppShell renders GoalAppFrame only on a route whose own id is on (route table pre-declared in goalSurfaces.ts and owned by design-core). No route ever shows a goal frame around a kit body, and the needs-shell rule stops a goal body inside a kit frame.
- Flags-on build in the required 'production build' CI job (VITE_GOAL_SURFACES=all pnpm build) compiles and prerenders with every surface on. A goal frame that calls useQuery or useAuth on /terms, /privacy and the other prerendered pages fails CI before it can land.
- Goal code lives only in new files under client/src/pages/goal/<id>/ and is lazy-loaded. Users with the flag off never download it, two surfaces never share a file, and one prefix serves the boundary test, the token audit's GOAL_SCOPE and the ownership check.
- Token audit widened: GOAL_SCOPE (scripts/designTokenAuditCore.mjs:24, today only /^client\/src\/components\/goal\//) adds client/src/pages/goal/, so R1 (no colour literals), R4 (no kit tokens) and R5 (no gradients) apply to moved pages. The boundary test stays two-way: kit files never import goal, goal files never import kit.
- Foundation removes every shared-line hotspot before fan-out: one frozen GoalShell prop contract (the #361 vs #360 conflict was 8 hunks); goalBoundary allows a folder instead of a per-surface regex line; useGoalShellMeta replaces PAGE_TITLES and activeNav edits in AppShell; one useCreditBalance hook replaces the two copies in #360 and #362; App.tsx is never edited by a surface.
- File ownership: owned paths are listed in each lane packet now and as an owns key once the picker accepts it. A CI scope check (fail-open on its own internal error, fail on a definite violation) refuses paths outside the task's owns read from origin/main, edits or deletions of existing tests, more than 12 changed lines in a kit page file, and any shared/** or server/** path in a surface PR.
- Pairwise merge-tree probe against every other open D-048 branch before landing. A non-zero conflict count means a boundary was crossed and goes to the CEO. GitHub's MERGEABLE flag only compares each PR with main: #362 shows MERGEABLE while it conflicts with #361.
- One landing at a time on the exact tested SHA, by fast-forward only, never the merge button and never squash. strict_required_status_checks_policy is false, so the merge button can land an untested merge commit, and a red main holds every lane (D-082, D-109).
- Tier 1 independent review on a draft PR for every surface that shows or moves credits or prices, signs in or verifies, shows identity, or reveals private data (inbox, queue, conversation, messages, profile, employer talent), plus the credits pill and every release row.
- Rule pins run with the flag on: login rule (loginRule, signIn, verify, referrer.otp), money copy imported from shared/moneyCopy.ts and never retyped, and pre-acceptance privacy (no seeker name, file names or message box before the referrer's own acceptance) on /queue, /inbox, /conversation, /email-review and /messages.
- Shell pins: no credits pill on referrer routes, decided by the server's verified-referrer verdict, never by the session's emails (D-055). A failed balance load says so and never shows 0 (D-063). Both pinned in appShell.test.tsx and landed Tier 1.
- Collision ordering: dependsOn the in-flight PRs that edit the same kit page. /queue waits for #353, #357 and #308; /ask for #308 and #357 (AskSent); /conversation for #353, #357, #375 and #314; /referrer-home for #314 and #382; /referrer/impact for #310; /invite and /suggest-company for #311; /landed for #314; /explore/:slug for #373 and #384; /plans for #359. Owner-blocked collisions (#324 on RequestDialog and Emails.tsx) are ported at release through the kit-drift check, not waited on.
- Kit-drift check before every release: any change to the kit page or its exclusive files after the goal version landed must exist in the goal version before the id enters RELEASED.
- Legal-text identity: the policy surface renders each legal page with the flag on and off and asserts identical text. Goal code imports the existing content and never copies it.
- Captures come only from synthetic fixtures (00_goal-*.json). kitScreenFixtures.test.ts bans the comps' sample names (Fernhill Bank, Kestrel Pay, the R-8F3K2 refs and the rest, D-071) and the retired pro/max plans.
- Fast rollback (about 6 min, a revert of one line) while the kit stays in the code; retirement only after 7 days live with no new Sentry issue.
- Branch hygiene: new row slugs must match no existing remote branch, because the picker resolves work by slug. The CEO closes the competing /explore builds (agent/instinct/goal-ui-w1-comps; agent/opencode/d048-phase-3-find, whose PR #363 is already closed).

## How rows enter the picker
- The foundation packet (`D-048-phase-3`) adds the `D-048-F-*` rows exactly as listed below, with its own packet path, in the pull request that lands the packet.
- Each lane packet (`D-048-P-*`) adds the rows of its clusters exactly as listed below (status `todo`, packet = that lane packet), in the pull request that lands the packet. Nobody else adds, removes or reorders rows (D-083).
- Release rows (`D-048-R*`) enter with status `owner`; retirement rows (`D-048-K*`) enter after their release lands.
- Before writing a money, sign-in, identity or privacy page, its packet re-reads the register: the money pages follow whatever D-110 to D-125 then say (levels, the credit dropdown, the monthly plan), not this table's notes.
- New row slugs must match no existing remote branch (the picker resolves work by slug).

## Methods considered (CEO ratings)
- **Audience lanes (one lane per user type: seeker, referrer, admin, employer, public): 6/10.** It works with the picker today, since lanes are free strings. But it is too coarse: work inside a lane is serial, and laneBusy (nextTaskCore.mjs:281) blocks the whole audience while any one of its PRs is open or waiting for review. Measured load is uneven: the seeker side holds about 27% of the code and 12 surfaces, employer about 5%. One audience becomes the critical path while others sit idle.
- **Page-level tasks with file ownership (one page or a small cluster per task and lane, owning only its own files): 8/10.** Above 7 because the code supports it: (1) lanes are arbitrary strings and laneBusy is per lane, so one lane per page or cluster runs in parallel with no picker change; (2) the import graph shows most pages already have disjoint exclusive folders (components/settings has 13 files, plus thread/, alerts/, verify/, requests/); (3) every measured conflict sits in a few shared hotspots: App.tsx line 113 (5,378 chars), goalBoundary.test.ts line 9 ALLOWLIST, GoalShell.tsx and goal/index.ts. One foundation PR removes them all. Not higher: ownership cannot be enforced until the picker accepts an owns key, and going all the way to one page per task (99 rows, about 22 h of serial landing) costs more than it buys. Clusters are the right grain.
- **Wave swarms (waves in order, every surface inside a wave in parallel, a gate per wave): 7/10.** Good for coherent QA and for batching owner design reviews, which D-048 requires before rollout. Wave releases keep the seeker journey consistent. Making gates block the next wave's builds adds a serial critical path the code does not need, so use waves only to order releases.
- **Contract-first layer split (one agent writes the shared contract, then an API agent and a UI agent build in parallel): 6/10.** The repo has the contract layer for it: shared/ holds Zod contracts such as shared/referrerAccess.ts and shared/askNote.ts, and AGENTS.md says to lock contracts before logic. Flagged-endpoint PRs like #373 and #384 already ship API work dark. But the standing owner rule (D-087/D-088) says every slice ships fullstack in one PR, so a three-PR split meets the intent only if each PR is dark behind the same flag. Web and API must also deploy from compatible source (invariant 6). A shared/** contract PR triggers both deploys, and deploy-api has a median of 16.4 min, which slows landings. It does not apply to D-048, which is client-only.
- **Many agents on one file: 1/10.** Git merges by line. App.tsx line 113 holds all 87 routes on one 5,378-character line, and the goalBoundary ALLOWLIST is one regex line. A read-only git merge-tree of #361 against #360 already gives 8 conflict hunks in GoalShell.tsx and goalBoundary.test.ts. Every extra agent on a shared file adds a guaranteed re-merge and another 4.4-min CI run. Never do it; give each shared file one owner lane.
