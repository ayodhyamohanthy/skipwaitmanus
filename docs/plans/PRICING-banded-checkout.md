# PRICING-banded-checkout: sell the D-219 banded plans and extra referrals

Status: packet, Nov 19 2026. Governing decisions: D-219 (frozen prices), D-366 (3) (the owner's word to sell, D-123), D-367 (the four open D-219 (8) answers). Prices live only in `shared/planFamily.ts` and `docs/PRICING.md`; this packet never restates a price.

## 1. Goal and why
The banded plans will let a seeker buy one of three plans (Early to Mid, Mid to Senior, Senior to Executive) or extra referrals at a level inside their band, in INR or USD, through Chargebee and Razorpay. The existing ledger tracks the allowance so a referral request spends in the frozen order. Catalog provisioning and storage prepare for checkout. Sales start after BANDED-release proves the purchase and recovery paths.

## 2. The owner's answers this build follows (D-367)
1. **Job level to band:** L1-L3 = Early, L4 = Mid, L5-L8 = Senior, L9-L10 = Executive (labels in `shared/jobLevel.ts` `JOB_LEVEL_LABELS`).
2. **Currencies:** INR and USD both at launch, both through Razorpay (international cards on the Razorpay account). PayPal is not the USD route for these plans.
3. **Gateway fees:** absorbed. The price shown is the price charged; no fee line.
4. **Founding cap filled:** undecided. Until the owner names a regular price, a band whose founding cap is reached stops selling (a plain "Founding places for this plan are taken" state), never an invented price.

## 3. Rules every row keeps
- Money paths are idempotent, reconciled and recoverable (AGENTS 0a): keyed ledger rows, webhook replay protection, a recovery path for a paid-but-not-credited checkout, refunds take back at most what was granted.
- One switch, `BANDED_SALES_ENABLED`, default `false`, declared in `.env.example`, passed through `src/worker.ts`. Every new route answers 409 `not_on_sale` before any provider call while it is off. The release row turns it on.
- Never sell an outcome; a referral is spent only when a verified employee can see the request (D-034); declines keep the spend (D-147).
- The superseded D-132 per-level credit cost (`ASK_LEVEL_COST`) stays off and unused.
- Referrer purchases stay refused (`REFERRER_PURCHASES_ENABLED = false`, D-055).
- No real-money QA: the Chargebee TEST site and Razorpay test cards only (`docs/PAYMENTS_TEST_RUNBOOK.md`).
- Senior to Executive is "by application" (`byApplication` in `shared/planFamily.ts`): checkout refuses it until an application is approved; the application flow is out of scope here and the plan shows "Apply" with no checkout.

## 7. BANDED-schema storage and rollout contract

- Stored `tokenBalances.plan` and `subscriptionCheckoutIntents.plan` append the three `PLAN_FAMILY_IDS`, preserving every legacy ENUM position. `WALLET_PLAN_IDS` and `INTENT_PLAN_IDS` follow those storage values; billable plan ids, prices and checkout request schemas do not change. Historical 0091 SQL stays unchanged; actual legacy ordinals are tested by applying the new migration.
- `bandedReferralBalances` has one row per user and referral level, with separate non-negative included-cycle and purchased balances. Included balance carries a cycle key and end date; purchased balance has no expiry. These are new empty tables, not grants or a conversion of existing money.
- `bandedFoundingCounters` stores issued and reserved counts per plan, bounded together by its frozen cap. `bandedFoundingMemberships` retains checkout-idempotency, reservation expiry and a unique bounded sequence on issuance. Only reserved places can release; an issued membership remains issued through lapse/cancellation, so account deletion must not cascade away its place. BANDED-checkout/grants must lock the counter row and mutate the reservation/issuance in one transaction. This row supplies constraints, no checkout or payment reader.
- Production order follows `docs/BRIEF.md`: deploy and verify a migration-only prerequisite before landing schema-dependent readiness. [PR #1395](https://github.com/ayodhyamohanthy/skipwaitmanus/pull/1395) and [Deploy API 44790210931](https://github.com/ayodhyamohanthy/skipwaitmanus/actions/runs/44790210931) fulfilled that prerequisite under D-371 (2). `0123_banded_plans.sql` has the same checksum on both merge parents. Runtime reconciliation uses SELECT queries only.
- TEST and LIVE use independent counter keys and uniqueness domains. Frozen caps are repeated only in database CHECK expressions, tested against `PLAN_FAMILY`; a test-site checkout cannot reserve a live founding place. User deletion nulls the issued membership's user link instead of deleting its counted sequence.
- Deploy migration `0123_banded_plans.sql` is under `drizzle/deploy/`, not the legacy root SQL journal: only deploy migrations reach production (`schemaDeployGuard`, GATE-migration-apply).
