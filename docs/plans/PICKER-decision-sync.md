# Packet PICKER-decision-sync: every agent works from the newest decisions, and stale work cannot be picked

> Read [`docs/BRIEF.md`](../BRIEF.md) first. Written by Claude Code as CEO (D-085, D-202) on Oct 23 2026 against `main` `9bd32abf`; its original line references are historical. D-200 (Oct 24) supersedes the CEO-only re-sync wording: any capable session may re-sync. Re-check file and line anchors against the latest `origin/main` before implementation. Lane `picker`, Tier 2. The register wins any conflict.

## Why (the owner, Oct 23: "every coding agent should know what's the recent up to date decision we took and sync; if it's old work it should not work, it should always work on the recent decision")
The picker tells a builder "Read docs/BRIEF.md, then <packet>. Read nothing else unless the packet names it." (`scripts/nextTaskText.mjs:42`). The same goes for takeovers (`:52`), fixes (`:72`) and landings (`:92`). Only the CEO review step reads the newest register entries (`:131`). So a builder can build a packet that a newer decision has changed. This has happened: D-035 was built and landed after the founder had held it (D-147), and plan names changed twice in a day (D-148, then D-152). Nothing in `docs/plans/assignments.json` records which decisions a packet was checked against, so the picker cannot tell stale work from current work.

## Rulings (D-202, with D-200's newer role rule)
1. **Each task records the newest decision its packet was checked against.** Add a key `syncedTo` (`"D-nnn"`) to every task in `docs/plans/assignments.json`. It is required on every task whose status is not `done`. Any capable session that writes or updates a packet sets it to the newest register entry checked, in the same commit (D-200).
2. **A decision that changes queued work names the tasks it changes.** From D-201 on, the register's "Supersedes · affects" cell of such an entry contains `Affects tasks: <id>, <id>` (exact task ids), or `Affects tasks: none`. Older entries carry no trailer and affect nothing in this mechanism.
3. **Out-of-sync work is withheld until it is re-synced, but re-sync is not CEO-only.** A task is *out of sync* when an entry newer than its `syncedTo` lists its id under `Affects tasks:`. No one may build, take over, make green, fix, review or land that task until re-sync; it holds no lane, exactly like a task whose dependency is not done (D-134). Any capable session may take the **re-sync**: read the newer entries, update the packet (or record in the register that the rule is unaffected), and set `syncedTo` to the newest entry, in one commit. D-200 supersedes the earlier CEO-only wording in D-202.
4. **Every agent sees the newest decisions before it works.** Every pick the picker prints, of every kind and for every role, opens with a block headed "Newest decisions (read before you work)". It lists the 5 newest register entries, plus every entry newer than the task's `syncedTo`, each as `D-nnn · YYYY-MM-DD · <title>`, and ends: "If any of these changes what your task says, stop and run `--report blocked \"<task id>: conflicts with D-nnn\"` (D-032). A newer decision always beats an older packet, note or chat message."
5. **The board shows it.** `--status` opens with the newest entry (`Register: D-nnn, YYYY-MM-DD`), and an out-of-sync task's row reads `re-sync (D-nnn)` instead of its state.

## What to build (red first, in `scripts/nextTask.test.ts`)
1. **Register parser** in `scripts/nextTaskCore.mjs`: `parseDecisionRegister(markdown)`, pure. Every line that starts with `| D-` must match `^\| D-(\d{3}) \| (\d{4}-\d{2}-\d{2}) \| `. A line that does not match throws an error naming the line number (fail loudly, never skip; AGENTS.md "Fix generators"). It returns `{ id, number, date, title, affects }` per entry, where:
   - `title` is the first `**...**` span of the row, else the first 160 characters of its third cell, with markdown stripped and cut to 160 characters.
   - `affects` is the comma-separated ids after `Affects tasks:` (each must match the task-id pattern; `none` gives `[]`), or `null` when the row has no trailer.
   - A duplicate id throws.
   Tests: real rows from the register (D-136, D-154), a malformed row, a duplicate, a trailer with two ids, `none`, no trailer.
2. **Loading:** `scripts/next-task.mjs` reads `docs/DECISIONS.md` from `LIST_REF` the way it reads the task list (`:208`, `tryGit("show", ...)`). A missing or unparsable register stops the picker with the parser's message, as a broken task list does.
3. **Validation:** `validateAssignments` (`scripts/nextTaskCore.mjs:127`) takes the parsed register. `syncedTo` joins `TASK_KEYS` (`:22`). It must match `^D-\d{3}$`, name an entry that exists in the register, and is required unless the status is `done`. Tests for each.
4. **Out of sync:** in `pickNextTask` (`:282`), next to `unmetOf` (`:302`), add `outOfSyncOf(v)`: the newer entries whose `affects` list `v.task.id`. Withhold the stale task itself from build, takeover, make-green, findings fix, review and landing, and do not let it make its lane busy (see `laneBusy`, `:306`, and the D-134 waiting rules). Add a pick kind `resync` after unblocks and before packets that any capable session can receive; no `isArchitect`/CEO-only gate. Tests: a non-CEO builder receives `resync` for an out-of-sync top `todo`; the CEO can receive it too; the stale task is not handed out before its packet is synced; an out-of-sync lane-mate does not block its lane; a task re-synced to the newest entry is handed out again.
5. **The newest-decisions block:** `scripts/nextTaskText.mjs` puts the block from ruling 4 at the top of every printed pick (build, continue, takeover, review, fix, make-green, land, packet, unblock, resync, CEO review, fix-main, wait). Tests: the block is present for each kind and lists entries newer than `syncedTo`.
6. **Data migration in the same pull request:** set `syncedTo` on every non-`done` task to the newest register entry on the `main` you merge with. That is a stamp, not a re-check: the tasks the CEO already re-synced in D-201 and D-202 are current, and the next re-syncs come through the mechanism. Name the number in the commit message.
7. **Docs in the same pull request (D-068):** `docs/BRIEF.md` "How to pick work" (keep the file under its 10 KB test, `scripts/briefContract.test.ts:21`, by tightening words, never by dropping a rule); `AGENTS.md` rule 6 and the system-map row "Agent work queue"; `docs/DELEGATION.md` (the register trailer, for packet writers); and the status line in this packet.
