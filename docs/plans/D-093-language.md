## 1. Goal

A job seeker in Hyderabad or Bhubaneswar, or a referrer in Bengaluru, can read skipwait.me in Telugu, Odia or Kannada instead of decoding English. Language is chosen by the person, from a list where every option is written in its own script (हिन्दी, not "Hindi"; no flag, because a flag names a country, not a language, and India alone has 22 scheduled languages). A detected browser language is offered once, never forced. Money, credit, legal and trust wording appears in another language only after a human has reviewed it; any string without a reviewed translation shows in English, so nobody ever sees a half-translated promise. This moves the north star (D-010, D-092: the global go-to site) by removing the language barrier at the two steps that decide whether someone gets referred: writing a referral request and deciding on one. Evidence in the register: CSA Research 2020 (76% prefer information in their own language). There is **no SkipWait user language data yet**, so the first slice (L1) builds a switched-off signup-language capture; it collects nothing until its privacy-contract qualification exists (R20), and only then can the language list after the D-093 six be ranked from data.

## 4. Target behaviour

Language model and data

- **R1. One language table, in code.** `shared/i18n/languages.ts` exports a readonly list of `{ tag, endonym, englishName, script, dir, status }` where `tag` is a BCP 47 primary tag (`en`, `hi`, `te`, `or`, `ta`, `kn`; `ar` present with `status: "hidden"`), `dir` is `"ltr" | "rtl"`, and `status` is `"live" | "hidden"`. Order is the D-093 order. `en` is always live and is the fallback.
- **R2. Endonyms are static strings, checked against CLDR in a test, never computed at runtime.** The test asserts each `endonym` equals `Intl.DisplayNames([tag]).of(tag)` under Node's full ICU, so a typo fails CI; the browser never needs `Intl.DisplayNames`.
- **R3. A language is offered only when it is `live`.** A language becomes `live` only when its catalogue (R9) has every key of the `reviewed` tier reviewed (R11). Until then the picker does not list it. While only `en` is live the switcher is not rendered at all (no one-option control), so shipping L3/L4 changes nothing visible. Work size, stated honestly: when L5-hi runs, `en.json` holds exactly the 8 L6 nav keys plus the 5 L4 switcher/offer keys = **13 keys**, none in the `reviewed` tier. So the first live language changes only the navigation labels and the language controls; every other string stays English until a later surface row (registered by a packet revision) keys it. Nobody should read "Hindi is live" as "the product is in Hindi".
- **R4. Persistence.** `AccountPreferences` gains `language: LanguageTag | null` (null = "use this device's choice"). Additive nullable column `accountPreferences.language varchar(16) NULL` (new migration in `drizzle/deploy/`, next free number at build time, plus the matching `server/schemaReconcile.ts` column entry). `parsePreferencesPatch` accepts `language` only when it is a `live` tag or null; anything else is 400 "Choose a language we offer". The existing 400 for unknown keys stays.
- **R5. Signed-out choice.** Stored in localStorage under the existing `sw:display-prefs` object (new `language` field; `readLocal` validates it against live tags). Storage failure keeps the choice in memory for the tab (same as today's fail-soft).
- **R6. Precedence (D-093 design spec).** (a) Signed in with a saved account `language` → that wins. (b) Signed in, account `language` null, and a local choice exists → the local choice applies **and is written to the account once** (that is "syncs to account on sign-in"; one PUT, idempotent, failure keeps the local choice and shows nothing). (c) No choice anywhere → English. Detected browser language never applies by itself (R7). Language is never derived from company domain, billing region, IP, `CF-IPCountry` or time zone.
- **R7. Detection is an offer, not a switch.** If no choice exists and the first `navigator.languages` entry whose primary tag is `live` and not `en`, the page shows one dismissible line at the top of the content, written **in the detected language with the English beside it** (e.g. "हिन्दी में देखें? · View in Hindi?"), with two text buttons: switch, and dismiss. Either action records `languageOffer: "accepted" | "dismissed"` locally and the line never returns on that device. No redirect, no URL change, no reload (D-093, Google Search Central "avoid automatic redirection based on language").
- **R8. Signup language capture (D-093 design spec "First:").** Behind one server constant `SIGNUP_LANGUAGE_CAPTURE_ENABLED = false` in `shared/signupLanguage.ts` (switched on only by `D-093-L1-release`, after the privacy-contract qualification in R20):
  1. **Cohort.** Only accounts whose `users.createdAt` is at or after `SIGNUP_LANGUAGE_CAPTURE_FROM` (an ISO timestamp constant set by the release row to its own switch-on time) **and** within 24 hours of their own `createdAt` at the moment of the write. An existing account, or one whose window passed, is never captured, whatever its columns hold. A null column therefore means "not captured", never "new signup"; the cohort is defined by `createdAt`, not by nullness.
  2. **Client-write contract.** `POST /api/account/signup-language`, authenticated (same `resolveIdentity` as the preferences routes), body parsed by a strict Zod schema in `shared/signupLanguage.ts`: `{ browserLanguage: string, preferredLanguageAnswer?: LanguageAnswer | null }` with unknown keys rejected; `browserLanguage` 2-35 characters and accepted only if `Intl.getCanonicalLocales(value)` returns exactly one tag (stored canonicalised); `LanguageAnswer` = one of the R1 tags (including hidden ones) or `"other"`. Responses: 401 signed out; 400 on any schema failure; 404 `not_available_yet` while the switch is off; **204 in every other case** (stored, already stored, or outside the cohort), so the endpoint is not an oracle for account age. Write-once per column inside one conditional `UPDATE … WHERE column IS NULL` (idempotent under retries and two tabs). The stored values appear in no API response.
  3. **Caller.** Only the start step (`Onboarding.tsx` / `GoalStart.tsx`) calls it, once, when the person completes or skips the step. `DisplayPrefsSync` is **not** used or changed by L1.
  4. **The signup language field.** One optional question in the start step, "Which language do you prefer to read in?", answers = the R1 endonyms (live and hidden) plus "Other", no default selected, skippable. It is shown only while `SIGNUP_LANGUAGE_CAPTURE_ENABLED` is true. Answering a not-yet-live language changes nothing else. **This question is a visible change**: L1 lands invisible only because the switch is off; `D-093-L1-release` is the row that makes it visible, with captures at 1280 × 900 and 390 × 844 and the D-150 check that the start step still has exactly one black commit.

Catalogue and runtime

- **R9. Catalogue.** Source of truth for runtime English is **the shipped component text on `main` at the moment a surface is migrated**, copied byte-for-byte into a hand-maintained source file per surface, `shared/i18n/source/<surface>.json`. `design/goal-ui/content.json` is a read-only design reference (§3.4): it is not machine-imported, because its values include fixture samples and design notes and it diverges from the UI. `shared/i18n/en.json` is generated from the `source/*.json` files only, by `scripts/build-i18n-catalogue.mjs`; no row in `docs/plans/assignments.json` owns `scripts/` as a folder and no row owns this new file, so L3 owns it and later rows change it only through a packet revision. Keys are stable dotted paths (`nav.find.label`), values are **whole sentences** (never concatenated fragments), plurals and selects per R10a, variables as `{name}`. Each other language is `shared/i18n/<tag>.json` with a subset of the same keys. The generator is the only writer of `en.json` (AGENTS "fix generators, not generated output"). Real size this implies: after L3, `en.json` is empty; L6 adds 8 keys; L4 adds 5; making the full app translatable means hand-classifying and keying several hundred strings surface by surface, each its own future row.
- **R10. Resolver.** `shared/i18n/t.ts` exports `createT(tag)` → `t(key, vars?)`: chain `tag → en`; a missing key in `en` throws in tests and returns the key in production with one Sentry event per key per release (no silent failure). A React hook `useT()` in `client/src/lib/i18n.ts` reads the current tag from the display-prefs store. No new dependency.
- **R10a. Message format contract (hand-written parser `shared/i18n/message.ts`).** Supported syntax is a strict subset of ICU MessageFormat; anything else is a generator error naming the file, key and character offset, raised at catalogue build time and in CI, never at runtime:
  1. **Arguments:** `{name}` where `name` matches `[a-zA-Z][a-zA-Z0-9]*`. A translation must use exactly the argument names its English value uses (no added or dropped argument).
  2. **Plural:** `{count, plural, =0 {…} one {…} few {…} many {…} two {…} zero {…} other {…}}`. `other` is required. Keyword categories must be in `new Intl.PluralRules(tag).resolvedOptions().pluralCategories` for that language (e.g. a `few` branch in `hi` is an error). Every category that list contains must be present or the message falls back to `other` for it, and the generator warns. Exact branches `=n` (non-negative integer) are allowed in any language. Inside a plural branch `#` prints the count formatted with `Intl.NumberFormat(tag, { numberingSystem: "latn" })`. No `offset:`.
  3. **Select:** `{role, select, seeker {…} referrer {…} other {…}}`; `other` required; keys match `[a-z][a-z0-9_]*`.
  4. **Nesting:** a branch body may contain arguments and at most one further plural or select level (maximum depth 2). Depth 3 is an error.
  5. **Multiple categories:** one message may contain several sibling plural/select blocks (e.g. two counts in one sentence); each is validated on its own.
  6. **Escapes (ICU apostrophe rules):** `''` prints one apostrophe; `'{'`, `'}'` and `'#'` print the literal character; a single apostrophe not followed by `{`, `}`, `#` or `'` is a literal apostrophe. An unbalanced quote or brace is an error.
  7. **Rejected:** `number`, `date`, `time`, `selectordinal`, `spellout` argument types, HTML or markdown in values, and any value longer than 4× its English length. Numbers, dates and money are formatted in code (R12), never inside a message.
  8. **Output:** plain text only; React renders it as text, never as HTML.
- **R11. Review tiers.** Every key carries a tier in `shared/i18n/tiers.json`: `reviewed` (money, credit/referral counts, price labels, checkout, refunds, trust and safety, verification, sign-in, privacy settings) or `standard`. Legal text (policy pages, legal notices) is never keyed in this packet and stays English. A non-English value for a `reviewed` key is used only when `shared/i18n/review/<tag>.json` records `{ key, sourceHash, reviewerRole, date }` and the `sourceHash` matches the current English. If English changes, the translation falls back to English until re-reviewed. Unreviewed `standard` strings may be machine-drafted, but a language is still not `live` until every `reviewed` key passes (R3). **Reviewer competence:** the reviewer of a `reviewed` key must be a native or fluent reader of the language **and** competent in the key's domain (how SkipWait money, credits and refunds work, verification and sign-in, privacy and trust and safety wording), because a fluent but uninformed translation can change a money or trust promise. The reviewer is recorded by role or public handle only (e.g. `native-hi-referrer-01`), never by name, email or other personal data (the repo is public). No paid translation service is used (D-031); if no qualified reviewer is available the language stays hidden (D-093 design spec: "unreviewed languages stay hidden"). This string review checks language and domain meaning. It is **not** the D-151 independent review: every Tier 1 row still needs a separate model that neither built nor fixed it to review the diff, whoever reviewed the strings.
- **R12. Formats.** Dates/times keep `displayPrefs` `formatDay`/`formatTimeOfDay` behaviour; when `dateFormat` is null they use the chosen language tag instead of `undefined` (device) as the Intl locale. Numbers use `Intl.NumberFormat(tag)` for grouping; **currency code and price amounts come from the server price data and billing region** (D-219), only the number grouping/glyph follows the language. Digits stay Latin (`numberingSystem: "latn"`) in every language, per the D-093 design spec ("LTR mono numerals with bidi isolation"), so referral counts and prices match across surfaces.
- **R13. Document attributes.** When the language changes, `<html lang>` is set to the tag and `<html dir>` to its `dir`. Prerendered public pages (`scripts/prerender-public-pages.tsx`) stay English with `lang="en"` in v1; locale URLs and `hreflang` are out of scope (§5).

Typography, layout, accessibility

- **R14. Fonts.** Each live non-Latin language loads its Noto Sans script font (Devanagari, Telugu, Oriya, Tamil, Kannada; Arabic later) **only when that language is active**, self-hosted from the `@fontsource/noto-sans-<script>` package (same publisher as the Instrument Sans and JetBrains Mono packages already in `package.json`, OFL licence, no cost), subset by `unicode-range`, `font-display: swap`, no font CDN. - **R16. Expansion.** No fixed widths on labels, buttons, nav items or chips; text wraps. Opens a list (GoalSheet on phone, menu on desktop) of live languages, each option the endonym with `lang="<tag>"` on the option element (so screen readers pronounce it correctly) and the English name as secondary text when the current UI language differs. Current one is marked with text + `aria-checked`/`aria-current`, not colour alone. 44 px rows, keyboard: arrows, Enter, Esc, focus returns to the trigger. Signed-out: in the `AppShell` signed-out `account.menu` slot, beside the "Sign in" button (§3.9). - **R19. Emails and notifications.** Transactional emails render in the account `language` when the template's keys are live in that language, else English; the subject and body never mix languages. `server/emailDelivery.ts` itself is unchanged; callers resolve copy via `createT`. Emails for signed-out recipients (e.g. work-email OTP before an account exists) stay English in v1.
- **R20. Analytics.** Two different things, qualified separately:
  1. **Client events (consent enforced here, not inherited from Clarity).** `language.offer_shown`, `language.offer_accepted`, `language.offer_dismissed`, `language.changed` (from/to tag only), `i18n.fallback_string` (sampled, key + tag, no user id).   2. **Signup-language capture and aggregation are new analytics and are not yet authorised.** Storing the R8 fields and computing any count from them (signups by browser language or answer, signup → first-referral-request completion by language) is new data collection about people. ## 8. Edge cases and races

- **Two tabs change language:** last write wins on the account; the other tab picks it up on next preferences load. No cross-tab broadcast in v1.
- **Choice made signed-out, then sign-in to an account that already has a different language:** account wins (R6a) and the local value is overwritten with it, so the next signed-out visit on this device matches the account.
- **A live language is later hidden (review lapsed):** stored tag stays; resolver falls back to English; the switcher shows English as current; PUT of that tag is refused. No data deleted.
- **Browser without `Intl.PluralRules` for a tag or blocked localStorage:** fall back to `other` form and in-memory choice; never throw.
- **Server preference load fails:** keep local/English, no banner (same as `DisplayPrefsSync` today).
- **Mixed-direction content:** seeker names in Latin inside Arabic UI and vice versa use `dir="auto"`; numerals isolated (R15).
- **Email language for a referrer whose personal and work aliases differ:** language is per canonical person (one `accountPreferences` row per `userId`), never per alias or company.
- **Migration:** additive nullable columns only; old code ignores them; boot reconcile adds them where the deploy SQL has not run; rollback = stop reading them.
