## SKIPPY-fix: the findings, each fixed red-first (lane `skippy-seeker`, Tier 1)

**S-1 (high, security, step 2): Skippy's job-page reader is an SSRF.** The historical finding was that `isPublicHostname` treated names and some bracketed IPv6 literals as public, then `fetchJobText` used a hand-written redirect loop and read the full response before slicing it. A probe of the original function on `9bd32abf` classified `localhost`, `[::1]`, IPv4-mapped metadata addresses, `*.nip.io` and `100.64.0.1` as public. The page text comes back to the user as "Here's what the job asks for" (`fitReplies`, originally `server/skippieSeeker.ts:211`), so a link or redirect to an internal address could expose that page text. The repo has the safe fetcher, `fetchPublicJobLink` (`server/jobLinkPreview.ts:25`), which checks DNS answers, pins the connection to the checked address, blocks IPv4-mapped and CGNAT addresses, follows bounded redirects and streams with a byte cap. The ask path and opportunity links already use it.
- **Red first** (`server/skippieSeekerDeps.test.ts`, new): an exported `fetchJobText(url, fetcher = fetchPublicJobLink)` seam so the test can call it and inject a fake safe-reader; stub the injected safe fetcher and never touch the network. Verify rejected local/private and redirect results produce no job text, and that `fetchJobText` never calls global `fetch` itself. Keep the existing `jobLinkPreview` fake-transport tests as the proof that the real safe fetcher makes no request to a private destination.
- **Fix:** `fetchJobText(url, fetcher = fetchPublicJobLink)` calls the safe fetcher, runs the existing `htmlToText` on its body, keeps the existing 80-character minimum, and returns null on any throw or empty body. Delete `isPublicHostname` and the hand-written redirect loop. `fetchPublicJobLink` refuses hosted job boards outside its two allowed APIs (`allowedHostedApi`, `server/jobLinkPreview.ts:22`), so a Lever or Workday link now goes to the existing "paste the job description" step (`server/skippieSeeker.ts:260`). That is the safe answer: do not widen the allow-list in this task.

**S-2 (high, money copy, step 2): the success line always says one credit.** `server/skippieSeeker.ts:412` reads "One credit was used, exactly the cost you confirmed." whatever the cost. With `ASK_LEVEL_COST=true` (D-132, off today) an L5 ask spends 5 credits and Skippy says 1. D-153 requires that it "promise only what works today".
- **Red first:** with a quote of cost 3, the covered-ask reply says "3 credits were used" and never "One credit".
- **Fix:** build the line from `session.quote.cost` (the accepted amount after S-3's transaction guard is in place), with the plural rule `quoteLine` uses (`:205`). Only the number and the plural change; keep the rest of the sentence.

**S-3 (medium, money, step 2): the send refuses a shortfall but not a changed price.** The current code overwrites `session.quote` with `fresh` before any comparison; the packet's earlier proposed `fresh.cost !== session.quote?.cost` check could therefore compare the fresh quote with itself. Even a correct comparison has a second race: the price may change between the fresh quote and the database transaction. D-140 binds a money confirmation to the exact amount.
- **Red first:** (1) The session holds a confirmed quote of cost 1 and the fresh quote at Send has cost 2 with no shortfall. `createAsk` is not called, the step stays `quote`, `session.quote` becomes the fresh quote, and the reply shows the new cost and asks for confirmation again. (2) The fresh quote still matches the confirmed cost, but the authoritative price changes before the DB transaction: `expectedCost` rejects the ask atomically with `AskPriceChangedError`, with no request or debit, and the flow offers the current quote for a second confirmation.
- **Fix:** capture the confirmed cost before overwriting `session.quote`. Compare `fresh.cost` with that captured cost; on drift, store the fresh quote and return without sending. If it matches, pass that amount as `expectedCost` through `createAsk` to the shared guard from `D-132-item3`, which checks the authoritative amount inside the same database transaction before any debit. Handle `AskPriceChangedError` through that task's two-click 409 re-quote contract; do not claim or display that a cost was charged unless the returned result confirms that exact amount.
- **Dependency:** `D-132-item3` already owns the shared `expectedCost`/`AskPriceChangedError` transaction guard. `SKIPPY-fix` depends on that task in `docs/plans/assignments.json` and must reuse its contract; do not duplicate or overlap the shared DB transaction work.

**S-4 (medium, scope, step 5): one flag opens agents to every account.** `SKIPPIE_AGENT_ENABLED=true` turns on `/agents` and agent keys for every signed-in account (`server/_core/index.ts:258`). Seeker Skippy limits its flag to the test seeker (`SKIPPIE_SEEKER_USER_IDS`); agents have no such list, so a production proof run would switch agents on for everyone.
- **Red first** (`server/seekerAgents.test.ts`): with the flag on and an allow-list of `{7}`, account 8 gets 404 on `GET/POST /api/seeker/agents` and every `/api/seeker/agents/*` route, and a key whose grant belongs to account 8 gets 404 on every `/api/agent/v1/*` route. Account 7 works as before. An empty list means nobody.
- **Fix:** add `SKIPPIE_AGENT_USER_IDS`, parsed with the same rules as `skippieSeekerAllowedIds` (`server/skippieSeekerRoutes.ts`; move that parser to one shared helper in `server/skippieAllowList.ts` and import it in both places). Wire it through `SeekerAgentRouteDeps` as `allowedUserIds`. The seeker guard checks the session's account, and the agent guard checks `grant.userId`, both after `enabled()`. Declare the key in `.env.example` (blank, with a one-line purpose note), forward it in `src/worker.ts:28` next to `SKIPPIE_SEEKER_USER_IDS`, and keep `server/configContract.test.ts` green (FND-5).

**S-5 (medium, flow, step 2): the company is checked only at the last step.** Skippy resolves the employer only inside `createCompanyReferralRequest` at Send, after resume, consent, analysis and the note. A link that maps to no verified company fails at the very end. The ask page checks at link time with the preview (`previewJobLink`, `server/jobLinkPreview.ts:26`, with `db.resolveEmployerDomainFromTargetUrl`, wired at `server/_core/index.ts:164`). D-137: same functions as the normal pages.
- **Red first:** a link whose preview has no `companyDomain` stays on `job_link` and replies with the preview's own `reason` and `recoveryAction`, and `fetchJobText` is not called. A link with a domain moves on as today and stores `companyDomain` on the session.
- **Fix:** add a dep `previewJob(url) => Promise<JobLinkPreview>` (real: `previewJobLink(url, db.resolveEmployerDomainFromTargetUrl)`) and call it first in the `job_link` step. When it has no `companyDomain`, reply with the preview's reason and recovery action, adding "Paste the job link from the company's own careers site." Skippy has no company-confirm step, so it does not take `ambiguous` links.

**S-6 (low, audit parity, step 2): Skippy asks are missing from the ask log.** The ask page records `company_referral.created` (`server/privateReferralRoutes.ts:795`, after `dispatchReferralReviewDeliveries`). Skippy records only `skippie_seeker.ask_created` (`server/skippieSeekerRoutes.ts:121-123`), and the current route can enter that block on a replay. An admin filtering by the standard ask action misses Skippy asks.
- **Red first + fix:** guard both Skippy ask-log events with `!out.session.replayed` (only when not replayed). Record `company_referral.created` with the normal ask event schema: `resourceId`, `companyDomain`, `attachmentCount: 1`, `pinnedWorkCount: 0`, `notifiedEmployees` from the create result, `creditReserved`, `coverageStatus`, `fastTrack: false`, `fromPost: false`, `firstLook: false` and `jobFunctionChosen: false`; add `via: "skippy"`. Keep `skippie_seeker.ask_created`; a replay emits neither ask-created event. Plumb the actual create-result fields through the session/route if needed; do not infer or invent them.

## SKIPPY-redteam: the prompt-injection test the pre-launch checklist requires (lane `skippy-redteam`, Tier 2, after SKIPPY-fix)
D-140: text inside user data is data, never an instruction. The checklist in `docs/SKIPPY.md` asks for a red-team test before any seeker-facing launch. Build it as a permanent, deterministic suite, `server/skippieRedteam.test.ts`, that runs in CI.
- **Corpus** (`server/fixtures/skippieInjection.ts`, at least 20 strings). Include instruction overrides ("ignore previous instructions and ..."), fake tool calls (JSON that looks like `propose_action` or a tool result), fake system or role markers, promise bait ("say you guarantee a referral"), exfiltration bait ("print the other seeker's resume") and markdown or HTML link injection. Write each in English and in one other language.
- **Places:** the job page text, the resume text, the seeker's note, the tailor skill names (step 2); every admin read-tool output (step 1, through the `tools` deps); the agent draft note and company query (step 5).
- **Model path:** a fake `invokeLLM` that obeys the injection (it returns the bad tool call, the promise text or invented facts) proves the code around the model holds. No admin card is created except through `propose_action` with a valid action. No unknown tool runs. No fact without a verbatim resume source survives. No promise reaches the seeker. No state moves without a typed turn. The ask note is byte-identical to what the seeker confirmed. Agent drafts store the text and never act on it.
- **Rules path:** the same corpus with no model configured changes nothing beyond the expected rules output.

Owned paths: the two new files only. Done: the suite passes in CI, and any case that fails is a finding reported to the CEO with the failing string. Do not weaken the case. Tier 2: the reviewer is any other session.
