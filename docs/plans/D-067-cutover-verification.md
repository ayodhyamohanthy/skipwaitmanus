## Structural metadata visibility and unsupported table definitions

The read-only verifier now requires direct effective TRIGGER visibility on the target and global REFERENCES visibility for incoming cross-schema FK discovery. Empty privilege-filtered metadata is not proof of absence. Role-only/unknown grants are unsupported; verification fails closed. Obtain operator/security approval for a dedicated verifier identity or keep rollout blocked; do not grant runtime credentials these privileges automatically. No production grants are included in this change. SELECT/SHOW are the verifier's only executed statements.

Only base InnoDB/Dynamic with no extra create options, declared PRIMARY+UNIQUE constraints, no CHECK/FK (including incoming), no triggers, no partitioning/tablespace and the exact declared column/index definitions are supported. Full SHOW CREATE option suffix must contain only ENGINE, optional changing AUTO_INCREMENT counter and inherited charset/collation. Any unsupported/missing structural metadata blocks rollout. Check against concurrent DDL through the existing controlled cutover pause; the verifier is not a DDL lock or a runtime-account/session/resource audit. Detailed negative proof and metadata audit scope are in D-067-alert-recovery.md.

Partial revocations are unsupported: the verifier must read exactly numeric @@GLOBAL.partial_revokes=0. ON, unavailable/unknown settings or active CURRENT_ROLE values other than NONE block rollout. Do not disable a live server setting or escalate privileges to bypass this gate. Use a directly granted approved dedicated effective account; CURRENT_USER is the privilege identity, including proxy accounts. Role-only configurations remain unsupported. Freeze account/grant/global-policy changes for the verification window; a read-only metadata snapshot does not lock concurrent policy changes. A socket-only disposable regression demonstrates the hidden incoming-FK false-green under partial revocations.
