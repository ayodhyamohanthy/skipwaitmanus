## Summary
- **Withheld under rule 1:** 2 findings (H-1, H-2). They are not described here. Their details are held for the CEO outside the repository. Their severity is not given here either, so this file says nothing about them.
- **Published:** 13 findings: 1 P2 and 12 P3. None has a path an attacker can use on their own. The P2 is an admin control that is weaker than its comments say, with no attacker path unless someone already controls the administrator's mailbox.
- **Held up under reading:**
  - **Webhook authentication.** The Chargebee webhook checks HTTP Basic auth with a constant-time compare before parsing anything (`chargebeeRoutes.ts:405-407`, `chargebee.ts:80-87`). The billing environment and its webhook secret come only from `BILLING_ENV` at startup, never from the request host (`chargebeeEnvironment.ts:28-50`). Razorpay deliveries are HMAC-SHA256-checked over the exact raw bytes with `timingSafeEqual`, and the route answers 503 when no secret is set (`paymentWebhooks.ts:43-48`, `:80-83`). PayPal deliveries fail closed with a 400 when a verifier rejects or errors (`paymentWebhooks.ts:152-158`).
  - **Gateway webhooks cannot mint seeker credit.** They only record activity and look up a checkout read-only (`paymentWebhooks.ts:112-124`). The one thing they can fulfil, B2B unlock credits, is bound to a server-created order and credited only when user, pack, amount and currency match that order and the pack price exactly, in one transaction with a single-winner state change (`db.ts:5589-5615`). Refund reversals are idempotent per refund id and capped at the captured amount (`db.ts:5642-5650`).
  - **Direct Razorpay and PayPal checkout fail closed** with 503 after sign-in (`payments.ts:155-165`).
  - **Every signed-in Chargebee route takes the user from the session**, never from the body. Credit recovery reads only the caller's own row by user, role and hosted page (`db.ts:4502`). Pass recovery refuses an intent that belongs to another user or role (`chargebeeRoutes.ts:331`). Cancellation looks up the caller's own subscription (`chargebeeRoutes.ts:244-246`). Recovery credits only a page the provider says is paid and whose intent id, amount and currency match the stored intent; anything else is parked for review (`chargebeeRoutes.ts:279-288`, `:359-373`). Referrer checkout is refused before any provider call (`chargebeeRoutes.ts:99`, `:164`), and gift checkout is off whatever the environment says (`chargebeeRoutes.ts:200`).
  - **Admin REST routes in scope check `role === "admin"` on the server-side account before any provider or database work:** catalog sync dry run and apply (`adminCatalogSyncRoutes.ts:28-31`, `:52-53`, `:66-67`), and jobs, abandoned-checkout close, money-check status, test alert, money-check run and admin Skippy (`scheduledJobsRoutes.ts:103-108`, `:135-140`, `:155-157`, `:171-176`, `:197-202`, `:231-237`, `:261-267`). The catalog apply also needs a JSON body that passes Zod, a typed site name that matches, and an unchanged plan hash (`adminCatalogSyncRoutes.ts:70-87`).
  - **tRPC admin procedures** (`community.listReferrers`, `ai.matchReferrers` in `routers.ts:34`, `:42`; `system.notifyOwner` in `systemRouter.ts:16-28`) all go through `adminProcedure`, which checks the role on the session user (`trpc.ts:31-38`). `matchReferrers` returns only referrers from the visible list, with names from the database, never from the model (`ai.ts:37-38`).
  - **The scheduled-jobs tick** needs an HMAC token derived from `JWT_SECRET`, answers 404 when it is unset, and is reachable only from the Worker, which strips the header on the public route (`scheduledJobsRoutes.ts:79-90`).
  - **Admin promotion is never granted on a self-asserted email:** the dev sign-in is excluded, and only a provider-verified address counts (`db.ts:120-126`).
  - **Cross-site requests:** the session cookie is `SameSite=Lax` (`_core/cookies.ts:19`), so a cross-site POST to an admin route carries no session. The abandoned-checkout close applies only on a JSON boolean `apply: true`, so a form post can at most preview (`scheduledJobsRoutes.ts:141`).
  - **Health routes** return no personal data and send `no-store` (`healthRoutes.ts:4-19`).

## Notes for the CEO
- Two observations outside this row's files: tRPC `auth.logout` (`routers.ts:22`) only clears the cookie, while `/api/auth/workos/logout` also revokes the session server-side. And the non-admin tRPC model procedures (`ai.copilot`, `ai.draftHiringManagerEmail`, `ai.referralFit`) have no rate limit. Neither is admin or money authorization, so neither is scored here.
- Referrer checkout refusal is keyed on the `role` named in the request body (`chargebeeRoutes.ts:99`, `:164`), so the same person can still buy on their seeker wallet. That matches the wallet-role model as written and is not scored, but it should be confirmed against D-055's intent.
