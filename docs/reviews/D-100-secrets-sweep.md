# D-100.secrets-sweep: secrets, tokens, codes and personal data in logs, Sentry, alerts, analytics and error bodies

Read-only audit (packet `docs/plans/D-100-security-audit.md`, row `D-100.secrets-sweep`, Tier 3). Auditor: Hark · 9976, 2026-10-30.
**`main` read:** `2d72dec7f1609b9e8a3b7e6ec6bc4062bb03aee0`. Every file:line below is on that commit.

## Result
No P0 or P1 finding. Nothing needed a private advisory under packet rule 1: every finding below is either reachable only by someone who already has operator access to the sink (the Sentry project, Cloudflare logs, the admin activity log, Clarity) or is latent behind configuration nobody has set. None gives an outside party a route, payload or token. Twelve findings are written out in full: four P2 and eight P3. The four P2s add sinks FND-4 did not reach. FND-4 scrubbed paths in explicit Sentry `extra`, the client event URL, client API-error events and the admin error-alert email. It did **not** reach the server SDK's automatic request data, client breadcrumbs, the slow-request log line or the workflow activity log.

Severity scale used here: P0 an outsider can exploit it now; P1 an outsider can reach personal data or a credential with modest effort; P2 a live credential, single-use token or personal data is stored in an operator-only sink (impact needs that sink to be read by the wrong person, or a processor breach); P3 hygiene, a latent issue behind misconfiguration, or a low-value leak.

## Checked and clean
- **Admin alert emails** (`server/errorAlerting.ts`): the route goes through `scrubTelemetryPath`, with query dropped, and the body says so. Payment, refund, card-validation and retired-plan alerts carry provider ids, amounts and reasons only. The two recipient addresses are the owner's own and are fixed in code. A Chargebee hosted-page id appears in the unmatched-payment alert; it goes only to the owner.
- **Daily money check email** (`server/dailyMoneyCheck.ts:14-18`): ids, amounts, currencies and reasons. No names, emails or request content.
- **Explicit Sentry contexts:** all 33 `captureServerError` call sites pass ids, area or route labels only. Client `readApiJson` (`client/src/lib/apiResponse.ts:5-12`) and `GoalEmailReviewAction` scrub their URLs.
- **Scheduled jobs:** stored and captured errors go through `safeJobError` → `redactReconcileLogText` (`server/scheduledJobRunner.ts:45-47`). The Worker's tick log (`src/worker.ts:105`) prints the job summary only. The public Worker strips the tick header and 404s `/api/internal/`.
- **Schema reconcile** logs use `formatSafeReconcileDiagnostic` (`server/schemaReconcile.ts:448`).
- **Sign-in:** no OTP, seeker code, password or reset token is logged. `reviewerLogin` logs the role only. The WorkOS callback logs stage, outcome or error name and a correlation id, with emails redacted from the stored diagnostic (`server/_core/workosAuth.ts:320-330`). The `debugToken` in `/api/auth/password/forgot` is returned only when `NODE_ENV === "test"`.
- **REST error bodies:** the `/api` JSON guard replaces any driver message with `GENERIC_SERVER_ERROR` for routes registered after it. The routes registered before it (`server/_core/index.ts:150-218`) return fixed strings. Catch-alls that return `error.message` (e.g. `server/privateReferralRoutes.ts:942,960,974`, `server/employerRoutes.ts:92`) can show a caller an internal non-driver message about their own request. That is cosmetic and no finding is raised.
- **Clarity identity:** `identifyClarity` sends the internal person id, never an email (`client/src/_core/auth.tsx:106-109`). The only custom events are the two impact-card copy events.
- **Activity log contents:** besides S-4 and S-7, metadata holds counts, domains, plan ids, reasons and ids. No email bodies, resume text or codes.

## Evidence
A local probe used the repository's pinned `@sentry/node` 10.75.0 and `express` from this commit's lockfile (no network; a fake transport collected the envelopes). Its shape: an ESM module that statically imports `express`, calls `Sentry.init` the way `server/sentry.ts` does (DSN, `environment`, `tracesSampleRate: 0.1`, nothing else), mounts `express.json()`, and calls `captureException` inside a POST handler. It sent placeholder values:
```
POST /api/x?code=QUERYSECRET   cookie: app_session_id=COOKIESECRET   authorization: Bearer BEARERSECRET   body {"code":"123456"}
captured event.request -> {"query":"code=QUERYSECRET","data":"{\"code\":\"123456\"}","cookies":{"app_session_id":"COOKIESECRET"},"auth":"Bearer BEARERSECRET","cookieHdr":"app_session_id=COOKIESECRET"}
```
The same result held with CommonJS, with `express` loaded before or after `init`. The production bundle (`esbuild --packages=external --format=esm`) was not run itself. The probe mirrors its import order. The SDK source confirms the mechanism: with `sendDefaultPii` unset, `defaultPiiToCollectionOptions` sets `cookies` to a deny list, never `false`, so `requestDataIntegration` includes cookies and headers, and the deny filter is applied only to span attributes, not to error events. Sentry's server-side default scrubber may still mask `cookie`, `authorization` and `password` keys at ingest. That depends on the project's settings, which were not checked, and it would not mask a field named `code` or free text.

S-8 on Node 22.23.3: `try { new URL("mysql://u:hunter2@ho st/db") } catch (e) { console.warn("[Database] Failed to connect:", e) }` prints `input: 'mysql://u:hunter2@ho st/db'`.
