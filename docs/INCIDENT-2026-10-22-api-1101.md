# Incident 2026-10-22: prod API returned Cloudflare error 1101 for about 10 minutes

## Timeline (UTC)
- 12:21 Deploy API for d5b95696 became the active Worker deployment (c704d312). 12:31: /api/health ok:true, commitSha d5b95696.
- 12:38:38 and 12:38:53: POST /api/admin/skippie/ask answered 404 (route present, flag off). So the container was answering.
- 12:39:25 onward: 503, then Cloudflare error 1101 (Worker threw) on every /api/* path. Web pages (Cloudflare Pages) stayed up.
- 12:41 diagnosis: DB reachable (read-only SELECT ok), no deploy in flight, active Worker deployment unchanged.
- 12:43 the last known-good run (39776430849, same SHA d5b95696) was re-run. migrate-db succeeded (idempotent). 12:49:23 /api/health ok:true again.

## What we know
- A secret write attempted at 12:38 failed with Cloudflare 10215 and changed nothing. It is not the cause.
- No new Worker deployment happened during the outage. Other branches uploaded preview Worker versions (not deployed).
- The database was healthy. No scheduled-job window fell inside the gap (hourly windows run at :00).
- No payment rows or webhook log rows exist for the gap. Sales are not live.

## What is NOT known
- The root cause. The most likely explanation is that the API container instance stopped or crashed and did not restart. This is NOT provable from what we can read: the deploy token has no container-status scope and Worker logs were not captured.
- Whether Chargebee or Razorpay attempted a webhook in the gap (provider dashboards not checked). Razorpay retries for up to 24 hours; Chargebee retries over several days; the chargebee-pending-reconcile job polls hourly.

## Follow-ups
- Alert: .github/workflows/api-health-watch.yml probes /api/health every 5 minutes and opens an "API DOWN" issue (GitHub notifies the owner), closing it on recovery.
- Open question: give the deploy token Containers read scope, or capture Worker logs, so the next container fault is diagnosable.
- Running into 10215 (a preview version newer than the deployed one) blocks secret writes. The deploy pipeline tolerates it (#444); manual secret writes do not.
