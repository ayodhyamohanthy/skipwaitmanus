## Independently Observed Conversation Remediation

On 22 August 2026, the persisted isolated-sandbox source was inspected directly in the Vibecode code editor after the agent's earlier remediation had initially addressed unrelated author-role and thread-cap findings rather than the two reported review gaps. The final inspected `backend/src/services/conversation.ts` contains a single generic authenticated denial helper returning `403 FORBIDDEN` with the body `You do not have access to this referral request.`. `openThread` returns `401` only when no actor exists; it returns the same generic denial for a missing profile, unknown request identifier, unrelated actor, cross-company or unassigned Referrer, and admin. A `409 CONVERSATION_LOCKED` response is guarded by a positive re-evaluation of `canAccessPrivateConversation` with an approved status, so it remains restricted to a still-eligible actual party and does not reveal locked state to a stale Referrer or another non-party.

The inspected `sendConversationMessage` transaction now re-fetches `id`, `status`, `seekerProfileId`, `referrerProfileId`, and `targetCompanyDomain` through `REQUEST_GATE_SELECT` immediately before message counting and insertion. It calls `canAccessPrivateConversation(actor, current)` on that fresh row, refuses deletion, reassignment, loss of verified corridor, status change, and missing second party, and re-derives the sender side from the fresh row. A `GateChangedError` carries the same response used by the initial check, so a race does not disclose that a request changed. The insert therefore occurs only after the complete current authorization gate passes.

The source-level tests were also inspected. `withStalePreRead` provides a stale permissive outer read while the Prisma transaction receives the real client and sees the changed row. Its cases cover deletion, reassignment to another Referrer, unassignment for the former Referrer, unassignment for the Job Seeker, target-company-domain change, and status closure; each asserts the generic denial and zero `ConversationMessage` rows. Additional direct reassignment coverage verifies that a formerly assigned Referrer cannot insert after loss of eligibility. This is synthetic SQLite-only coverage; it does not use OTP, email, external services, production data, or deployment.

The visible bounded command output reported `bunx prisma generate` and `bunx prisma db push` success; a repeat focused `timeout 90 bun test src/conversation.test.ts` run with **32 pass / 0 fail / 313 expectations** in 2.03 seconds; and `timeout 180 bun test` with **522 pass / 0 fail / 3,588 expectations** in 8.48 seconds. Backend typecheck and webapp typecheck/build succeeded. The system-managed local dev server was unavailable, so no health `200` claim is recorded for this remediation. Post-run synthetic counts were zero for conversation, referral-request, notification, document, profile, user, session, account, and verification tables; retained privacy-safe activity events remained, with null actors after fixture cleanup. No production boundary was changed.
