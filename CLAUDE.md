# Instructions for AI coding agents

**Read [`docs/BRIEF.md`](./docs/BRIEF.md) first** — the one-page brief every AI model starts from (D-073). The full rules follow; they win any conflict with the brief.

**Owner says `build`, `resume`, `continue` or `next`?** Continue current work, never restart an old plan. First follow [the current-instruction preflight](./docs/BUILD_CONTINUITY.md) (D-225): fetch current main, read latest instructions and decisions plus the previous repo-only outcome, check goal alignment and ownership, then use `node scripts/next-task.mjs --claim "<your model name>"`. Read its assignment against those decisions before implementation; stale or conflicting context holds only the affected task. Claude handles intelligence/reasoning; other tools develop. Keep the picker's exact session-tagged name for later flags. The picker is not proof that the preflight was read.

**Claude session role (D-225, owner, Oct 28).** Use this session for intelligence and reasoning: read the current instructions, latest decisions, previous repo-only outcome and board; diagnose the highest-value gap and return a bounded, goal-aligned decision or implementation handoff for another tool. Earlier D-109/D-200/D-203 wording permitting Claude implementation is superseded for this role. Do not start implementation merely because the picker offers it. The historical identity `--claim "Claude Code"` is not a role exemption; use the picker's supported `--avoid <id>` for work this session must not take, rather than blocking it for every developer. Other tools continue authorized development without waiting for Claude. Never reopen the owner's frozen decisions, change prices or legal text, spend, or waive independent review/CI.

**D-206, the session-start re-rating (owner, Oct 23; binding).** At the start of every session, after the board, re-rate our decisions 1 to 10 against the goal: the go-to global site for job referrals, getting people referred faster. Cover every entry since the last review, every decision the top five open tasks rest on, and the next 20 active entries that have gone longest without a review. Fine-tune anything below 10 that is yours to decide, as a new entry with `Affects tasks:`. Bring anything owner-reserved to him, rated. Append the session's ratings and actions to `docs/plans/DECISION-REVIEW.md`, so the next session starts where this one stopped. **D-205:** GitHub and every clone stay in sync; a branch that is done and merged is deleted online and offline (`docs/plans/BRANCH-HYGIENE.md`).

All instructions for this repository live in [`AGENTS.md`](./AGENTS.md) — read it first, starting with section 0, together with the decision register [`docs/DECISIONS.md`](./docs/DECISIONS.md) (a newer entry wins where it amends an older one; it wins over every other doc).
Pick work only from the priority queue in [`docs/KIT_V4_BUILD_PLAN.md`](./docs/KIT_V4_BUILD_PLAN.md) §3b through the picker: it claims on origin, your first commit on the task branch sets the §3b row (or, when several tasks share that row, your line in the packet's Status section; the picker says which, D-134), which reaches `main` with the work, and a claim nobody pushed to (commit or `--heartbeat`) for 2 hours is free (D-083, D-085). Every change updates every affected markdown doc in the same push (D-068).
Push to `main` only when everything is green (D-082): `main`'s latest CI, the full gate on your commit merged with `origin/main`, and GitHub CI on that exact commit (pull request first). A docs/registry-only PR needs focused checks, a separate independent delta review and required CI instead of a fresh full gate each time `main` moves (owner merge-policy amendment, Oct 23). While `main` is red, push nothing but the fix.
